A person can ask a question, take a detour, change their mind, and return to something they mentioned twenty minutes earlier. The meaning of their next message depends on that history. “Continue” is a perfectly reasonable request when both participants know what was interrupted.

A single prompt leaves most of this out. That is useful for some evaluations, but it limits what we can learn about an assistant that is meant to collaborate over time.

## Conversations have a shape

Imagine a conversation about designing a study. It starts with a research question, branches into measurement, detours into participant recruitment, and then returns to the original hypothesis. The final turn may contain only a few words, but interpreting it requires recovering an earlier thread.

A conversation can be described as a graph of topics and revisits. This would be an abstraction, not a perfect representation of meaning. Its usefulness would depend on whether the structure helps us create and distinguish demanding interactions.

Three dimensions seem worth separating:

- **Depth:** how far a thread develops before it changes direction.
- **Breadth:** how many distinct threads remain relevant.
- **Revisits:** whether an earlier thread is resumed with its constraints intact.

Length alone cannot distinguish these. A long exchange about one topic may require less coordination than a shorter exchange that crosses several unfinished threads.

## What should a simulator preserve?

A useful simulated user would need more than a speaking style. It might have a goal, incomplete knowledge, preferences, and reasons to change direction. Its behavior should remain connected to these properties over multiple turns.

The challenge is deciding which properties matter for the evaluation. A simulator designed to test memory might hold preferences stable. One designed to test adaptation might change a preference and provide a reason. Mixing the two carelessly could make failures difficult to interpret.

## A small evaluation pair

In one conversation, the user says, “Let’s go back to the first option.” In another, they say, “Let’s go back to the first option, but keep the new constraint.” The assistant needs to recover the option in both cases. Only the second requires combining an earlier branch with later information.

Success should be judged against the conversation state, not against a polished-sounding response. Did the assistant recover the right option? Did it preserve the applicable constraint? Did it invent a preference that was never stated?

## Questions before scale

Before generating thousands of conversations, I would want to inspect a small set in which each branch and revisit has a clear purpose. This makes it easier to see whether the evaluation is testing continuity, reasoning, or merely familiarity with a phrase.

The broader ambition is to evaluate an assistant as a participant in an ongoing exchange. That starts with taking the other participant seriously—even when that participant is simulated.
